# 拆分结果与稳定边界

实际栈为 TypeScript、Three.js、Vite，宿主有独立 Node.js/SQLite 服务；没有引入 React 或另一个游戏引擎。此次从既有源码提取表现层，不重写业务。

| 类别 | 权威位置 | 协作范围与边界 |
| --- | --- | --- |
| A 核心游戏 | 私有宿主的控制器、服务端世界与业务模块 | 身份、位置、碰撞、导航、门禁、多人事件、任务、审批和计酬继续由宿主管理 |
| B UI 表现 | `src/ui/` | HUD、10个前端工作流模块与共用样式；宿主注入请求、打开面板、生命周期和移动回调 |
| C 场景表现 | `src/office.ts` | Three.js 建筑、灯光、家具与通用角色；独立 Root 可替换，不重建员工对象 |
| D 素材 | `public/`、`source/blender/` | 13个家具、解码器、许可；家具库是从 GLB 整理的派生 Blender 工程。私人肖像不含在内 |
| E 装修数据 | `themes/*/theme.json` | 分别选 UI、环境和通用角色配色；白名单模型映射、颜色和灯光参数，没有主题脚本 |
| F 稳定接口 | `src/layout-contract.json` 与宿主实际动作服务 | 工位/房间 ID、锚点、楼梯、碰撞与门禁固定；布局变化必须先设计迁移，不能当成普通换肤 |

宿主 `scene.ts` 持有角色、相机、输入、本人私人模型与运动状态；只委托 `OfficeVisuals` 建立装饰。换主题先在临时 Scene 完整加载，成功后替换旧 Root；失败保留旧装修。宿主构建按资源目录清单复制，复用一份 Three.js。

展厅使用少量明确标记的合成资料来展示共用 UI。全部业务写入被拒绝，不能通过展厅登录真实公司或保存稿件。原有前端视图仍服务于既有 API，并未在此次任务中抽象为一个全新的通用表单框架。

协作发布流程：设计分支 → 自动检查与截图 → 人工审查源码和素材 → 合并 → 宿主固定提交 → 宿主业务测试及预发布构建 → 正式切换。PR 不自动部署，游戏不会在线执行远程主题脚本。

当前主题系统覆盖颜色、灯光、受限家具映射和通用角色配色。新增任意地图、完整人形骨骼换装、在线装修商店和多人共同编辑不在本次实现范围。
